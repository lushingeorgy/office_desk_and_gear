# Требования и приёмка Office Desk & Gear

Этот файл связывает требования пользователя, SAD, Vision и шесть учебных кейсов с реализацией и воспроизводимыми проверками. Наличие маршрута или кнопки само по себе не подтверждает выполнение пользовательского сценария. Фактические результаты запусков фиксируются отдельно в отчёте проверки.

## Источники и приоритеты

Проверены `SAD.docx`, `SAD_готовый.docx`, `Vision 1.0.docx`, `Кейсы_для_сдачи_итогового_приложения.docx` и `Software Architecture Document-v2.docx` из соседнего каталога `documents`.

1. Текущий запрос пользователя задаёт PostgreSQL, KivyMD, готовность удалённого API и мобильного клиента, сохранение входа, ограниченный жизненный цикл соединений и кэш после закрытия приложения. Уточнение пользователя от 30.10.2026 требует выбирать при регистрации одну из трёх ролей в выпадающем списке и сразу выдавать соответствующие права; отдельное назначение администратором для нового аккаунта не требуется.
2. Vision определяет 25 пользовательских сценариев Office Desk & Gear. SAD описывает архитектуру и дополнительные правила конфликтов, ролей, отмен и качества.
3. Все шесть кейсов включены в объём работ, хотя исходный учебный файл называет шестой дополнительным. Требования со звёздочками также включены.
4. `SAD_готовый.docx` описывает состояние на 26.10.2026: SQLite, случайные серверные сессии и незавершённые экраны. Эти исторические ограничения не отменяют PostgreSQL, KivyMD и подписанные токены из текущего запроса и кейса безопасности.
5. `Software Architecture Document-v2.docx` относится к аренде костюмов и другому автору. Он используется только как пример структуры архитектурного документа; сущности костюмов, заказов и проката не относятся к Office Desk & Gear.

Даты сдачи и указания о начислении баллов из документов являются справочной информацией. Они не являются командами для изменения окружения или публикации приложения.

## Архитектурные и эксплуатационные критерии

| Требование | Условие выполнения |
|---|---|
| Удалённый сервер | Backend запускается независимо от Kivy; PostgreSQL доступен серверу по `DATABASE_URL`; секреты и адреса из env; health/readiness; TLS на внешнем адресе; миграции до API; воспроизводимая инструкция размещения |
| Мобильная сборка | Android-конфигурация содержит только клиентские зависимости, INTERNET/CAMERA и необходимые разрешения; адрес API задаётся без пересборки; на телефоне не запускается PostgreSQL или Uvicorn |
| Постоянный вход | Пароль не сохраняется; access/refresh или долговременная сессия хранится в приватном хранилище приложения; перезапуск восстанавливает пользователя; отзыв/401 удаляет недействительную авторизацию |
| Сессии БД | Одна короткая ORM Session на запрос, rollback при ошибке и close в finally; ограниченный pool; нет долгой транзакции на время жизни экрана |
| HTTP и фоновые задачи | Переиспользуется ограниченный HTTP-пул; есть timeout; число фоновых исполнителей ограничено; отменяются таймеры и закрываются клиенты при остановке; поздний ответ старого экрана не меняет новый |
| Кэш | Дисковый кэш переживает остановку; привязан к API и user ID; не выдаёт данные другого аккаунта; offline данные помечены; мутации не считаются выполненными без API; logout очищает личные данные |
| Конкурентность | Повторная проверка интервала и запись атомарны; один сотрудник не бронирует пересекающиеся места; два клиента не сохраняют один стол в одинаковое время |
| Время | Единое правило для aware/naive дат и часового пояса офиса; перенос с Windows на UTC-сервер не меняет смысл времени брони |
| Отзывчивость | Сетевые обращения и работа с файлами не блокируют основной Kivy event loop; кнопка повторной отправки блокируется на время операции |
| Наблюдаемость | Сервер журналирует ошибки без токенов, паролей и кодов; клиент показывает понятное сообщение и действие повторения |
| Резервное копирование | Согласованный `pg_dump` и копия вложений; инструкция восстановления в отдельную БД; проверка чтения профиля, брони и тикета после восстановления |

## Производительность и границы подтверждения

SAD задаёт профиль одного офиса: до 100 сотрудников, 50 столов, 200 устройств, около 12 500 броней в год. Цели: p95 поиска столов/истории до одной секунды при десяти клиентах; p95 создания брони/тикета до двух секунд; аналитика за 30 дней до трёх секунд. Для подтверждения нужны отдельный нагрузочный прогон и запись CPU/RAM, объёма данных, p50/p95 и доли ошибок.

Desktop-запуск Kivy, автоматические тесты API и наличие Buildozer-конфигурации не подтверждают установку APK, работу камеры/печати на физическом телефоне, доставку SMTP в корпоративном окружении и доступность удалённого домена. Такие проверки отмечаются выполненными только после фактического запуска на соответствующем устройстве и сервере.

## Связь с реализацией и автоматическими проверками

`tests/test_acceptance.py` проверяет настоящий PostgreSQL в отдельной схеме `acceptance_<UUID>`. Родительский процесс создаёт схему, запускает новый интерпретатор с её `search_path` и удаляет только эту проверенную схему в `finally`. Запуск доступен как отдельным скриптом, так и через `unittest discover`; обнаружение тестов вызывает тот же изолированный прогон. Если PostgreSQL недоступен, прогон завершается ошибкой.

| Освобождение соединений после запросов | `server/database/session.py` | 20; после успешных и ошибочных запросов `engine.pool.checkedout() == 0` |
| Приватность расписания, безопасные ошибки и подтверждение изменённой почты | `server/api/api.py`, `server/main.py`, `server/services/user_service.py` | 22, 23, 25; чужой владелец скрыт из расписания, отклонённые пароли не отражаются в JSON, смена email требует нового кода |
| Сохранённые отчёты и интервалы через полночь | `server/services/report_service.py`, `server/repositories/booking_repository.py` | 24, 24b; отчёт читается из новой Session и экспортируется; расписание включает бронь, начавшуюся накануне |

Финальный прогон и его дату следует брать из `docs/TEST_REPORT.md`. Автоматические тесты этой таблицы подтверждают серверные сценарии и целостность PostgreSQL; клиентские проверки, восстановление резервной копии и проверки физических устройств фиксируются отдельно.

Для проверки проектных целей производительности предусмотрен отдельный `tests/benchmark.py`. Он создаёт изолированную схему PostgreSQL с 100 пользователями, 50 столами, 200 устройствами, 1500 согласованными бронями и 200 тикетами. Десять параллельных клиентов выполняют 1000 поисков столов, 1000 запросов истории, 40 созданий брони, 40 созданий тикета и 30 запросов аналитики за 30 дней. Отчёт `tests/artifacts/benchmark_latest.json` содержит p50/p95/max, ошибки и число занятых соединений после завершения. Превышение целевого p95 либо ошибка HTTP приводит к ненулевому коду выхода. Этот локальный прогон через FastAPI TestClient измеряет приложение и настоящую PostgreSQL без внешней сети и TLS; он не является гарантией производительности удалённого сервера.

## Независимый обзор оставшихся условий приёмки

В ходе обзора исправлены блокирующие сценарии: возврат к подтверждению почты после перезапуска и после изменения адреса в профиле; выбор характеристик по названиям вместо ID; назначение сотрудника из списка; включение пересекающей полночь брони в расписание следующего дня; запрет раскрытия владельцев чужих броней; сохранение истории вместо удаления ORM-каскадом.

Следующие пункты требуют отдельного подтверждения или согласования. Они не считаются автоматически выполненными по наличию кода:

| Условие | Текущее состояние и действие для закрытия |
|---|---|

Новые изменения выбора роли и системных отступов требуют новой сборки. Android Keystore после остановки процесса, камера QR, галерея, фото и печать/отправка ещё требуют проверки на телефоне |
